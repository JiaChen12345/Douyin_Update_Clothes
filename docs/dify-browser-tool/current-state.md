# 多平台 Dify 改造：现状检查

> 检查日期：2026-10-14。仅记录现有代码和本轮需求分析，不代表新工具、工作流或视觉模型已经实现。

## 现有调用关系

```text
Python 桌面界面 / Python 命令行
  → AutomationRunner
  → 持久化 Edge 浏览器会话
  → 根据来源链接选择素材下载适配器
  → 下载包落盘 → 解压及整理素材
  → 根据目的平台选择：
      抖店：DouyinDraftCreator 固定操作
      搜款网 / 17网：OperationReplayer 录制回放
  → 保存草稿 → 状态、日志和截图
```

Node.js 是另一个旧入口，按来源下载适配器取得素材，再执行抖店草稿流程。

在已检查的项目源文件、根目录文件和文档中，未发现 Dify 工作流 DSL、Dify 客户端、HTTP 浏览器后端或视觉模型接入。当前不存在可以直接调整的 Dify→Python 调用关系，需增量增加接入层。两个现有 Dify 相关文档是待审批需求草案。

| 最终业务动作 | 旧流程只保存草稿；`operation_recorder.py:26` 检查禁止动作 | 新入口按用户要求增加人工最终确认；旧入口仍保持草稿边界 |

### 平台路由需要区分来源和操作目标

当前 `Adapter.matches` 按商品链接识别素材来源；`process_task` 的 `destination` 则表示上款目标网站。搜款网和17网的旧上款任务要求来源链接为淘宝或天猫。

新工作流的 `platform` 必须表示本次实际操作的平台，不能把来源站点适配器名称直接当作目标平台路由。链接与已打开页面也须校验所属平台。

### 两个应在新执行层修正的具体行为

1. `operation_replayer.py:106` 的坐标兜底路径先点击并返回，未经过后续的正式发布文字检查。新入口的坐标操作必须和语义操作共享最终动作确认检查，不能直接照搬该路径。
2. VVIC 分支先等待第一个文件保存，再为第二个文件安装下载等待。根据代码顺序判断，连续下载可能在第二次监听前已经触发；新下载管理需要在首次点击前接收相关下载事件，并等待已捕获的文件全部保存完成。

## 本轮职责边界

| 层 | 应承担的逻辑 |
|---|---|
| Dify | 输入解析、平台路由、平台步骤顺序、是否需要视觉、异常分支、重复公共节点及结果输出 |
| 视觉模型 | 根据当前截图及关键词／参考图返回指定目标识别结果；不规划任务、不全量分析页面 |
| 本地 Python | 会话与任务管理、参数及结果校验、坐标换算、最终确认检查、目录与文件管理、执行记录 |
| Playwright | 可靠 Locator 查找、页面截图、鼠标及表单交互、下载事件和实际结果检查 |

## 方案比较

| 方案 | 取舍 |
|---|---|
| 推荐：增量增加轻量工具接入层，复用现有平台与公共执行能力 | 最符合保留旧项目、三个分支独立和控制模型成本的要求 |
| 直接把旧完整任务作为一个工具调用 | 初期接入简单，但 Dify 无法在每步间观察、判断目标或处理页面分支，不满足本轮灵活定位要求 |
| 用通用视觉 Agent 全面替代旧流程 | 增加模型调用、组件分析和维护负担，与用户指定的轻量定向识别约束不符 |

推荐的流程行为是：校验输入及平台 → 相应平台步骤 → 尝试可靠的目标 Locator → 无可靠目标时截图并定向识别 → 检查当前页面与定位结果 → 执行 → 验证 → 按需下载落盘 → 返回结果。具体接口与节点配置在需求获批后的技术计划中确定。
